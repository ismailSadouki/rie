The protocol that actually works, for a working engineer: ``` THE 4-PASS PROTOCOL (per important paper, ~4-6 hours total) PASS 1 — SKELETON (20 min): Abstract, figures, tables, conclusion only. Decide: is this worth deeper time? (80% are not) PASS 2 — ACTIVE READ (90 min): Read fully with a notebook open. Write down: • What problem, precisely? • What's the one equation that matters? • What did they ablate? What did they NOT ablate? • What would break at 10x scale? PASS 3 — CODE (2-3h): Read the official implementation OR implement the core idea yourself in ≤100 lines. For LoRA, DPO, FlashAttention — implementing beats reading. PASS 4 — TEACH (30 min): Write 5 bullet points as if explaining to a colleague. If you can't, you didn't understand. ``` **Answers to your specific comparisons:** - **Reading papers only:** worst option alone. Retention ~10%. - **Annotated papers:** good for the 5-10 foundational ones (Annotated Transformer, lilianweng.github.io posts). Don't overuse — it's someone else's compression. - **Code first:** surprisingly effective for engineering-heavy papers (vLLM, FlashAttention). Weak for theory papers. - **Paper then implementation:** the best default for you. - **Reimplementing:** the gold standard, but expensive — reserve for ~10 papers a year, chosen carefully. - **Conference talks:** use for orientation on new areas only, never as a substitute. **Your canonical 12 papers** (read these with the 4-pass protocol, in this order): GPT-2 → GPT-3 → Chinchilla → InstructGPT → LLaMA → LoRA → FlashAttention → DPO → QLoRA → PagedAttention (vLLM) → Llama 2/3 technical reports → "Textbooks Are All You Need" (for data-quality thinking). --- # Part 5 — Open Source **Yes, but with precision.** One merged PR in a respected repo is worth more on your resume than three toy projects — because it proves you can read unfamiliar code, meet a bar set by senior engineers, and survive code review. LLM engineering optimizes for: clean pipelines, evaluation design, and systems that generalize. These are nearly opposite skill sets. A Kaggle medal tells an LLM hiring manager almost nothing — I've never seen it discussed positively in a hiring debrief for an LLM role. **The exception:** recent LLM-specific competitions (e.g., the LMSYS-style prediction competitions) force you to work with real LLM outputs, build evals, and handle messy generation data. Practice the 20-minute Pass 1 from Part 4 on 5 papers a week. 2. **Experimental methodology.** This is where your statistics background is a genuine weapon. Most ML researchers run sloppy experiments: one seed, no controls, confounded ablations. If you bring proper experimental design — multiple seeds, controlled comparisons, honest error bars — you are *already* better than the median published author. This is your differentiator; lean into it. 3. **The reproduction-to-extension ladder.** Step 1: reproduce a known result at small scale. Step 2: find the assumption the paper didn't test. Step 3: test it. That's a workshop paper, and it's how most first publications actually happen. 4. **Ablation discipline.** Learn to ask: "what's the cheapest experiment that could falsify my hypothesis?" Run that one first. This habit alone puts you ahead of most people. 5. **Scientific writing.** Start a public engineering log *now* (blog/Substack/GitHub READMEs). Every project write-up is practice for paper writing. Researchers who can't write don't get cited. 6. **Benchmark skepticism.** Read eval papers critically — contamination, saturation, Goodharting. Knowing why MMLU is weak signal is itself valued knowledge. --- # Part 9 — The Traps (I've Watched People Lose Years to These) ``` TRAP 1: TUTORIAL HELL Symptom: 40+ hours of video, zero repos.
