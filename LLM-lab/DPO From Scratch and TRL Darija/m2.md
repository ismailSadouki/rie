### 1. "Get the Qwen policy model running"

Load the model that you are actually going to **train with DPO**.

For example:

```python
policy = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen2.5-0.5B-Instruct"
)
```

The **policy** is:

[  
\pi_\theta(y|x)  
]

where (\theta) are the parameters you will update.

---

### 2. "Add LoRA/4-bit if desired"

Your GPU memory is limited, so instead of training all parameters:

[  
\theta \rightarrow \theta'  
]

you can use **LoRA**, where the original model is frozen and you train only small adapter parameters:

[  
\theta_{\text{model}} \text{ frozen}  
]

[  
\phi_{\text{LoRA}} \text{ trainable}  
]

And **4-bit quantization** reduces the memory used to store the base model.

So the practical setup could be:

```text
Qwen model
   ↓
4-bit quantization
   ↓
frozen base model
   ↓
LoRA adapters
   ↓
train only LoRA parameters
```

This is mainly about making DPO fit on your T4.

---

### 3. "Establish how we will obtain the reference model's log-probabilities"

This is the important DPO part.

DPO needs two policies:

[  
\pi_\theta  
]

= **policy model** → trained

and

[  
\pi_{\mathrm{ref}}  
]

= **reference model** → frozen

For each chosen/rejected response, you need:

[  
\log \pi_\theta(y_w|x)  
]

[  
\log \pi_\theta(y_l|x)  
]

and also:

[  
\log \pi_{\mathrm{ref}}(y_w|x)  
]

[  
\log \pi_{\mathrm{ref}}(y_l|x)  
]

These are then used in the DPO loss:

# [  
\mathcal L_{\mathrm{DPO}}

## -\log\sigma  
\left(  
\beta  
\left[  
\log\frac{\pi_\theta(y_w|x)}  
{\pi_{\mathrm{ref}}(y_w|x)}

\log\frac{\pi_\theta(y_l|x)}  
{\pi_{\mathrm{ref}}(y_l|x)}  
\right]  
\right)  
]

So **"establish how we will obtain the reference log-probabilities"** means deciding:

> How do we calculate the (\pi_{\mathrm{ref}}) terms without running out of GPU memory?

You have two main choices:

```text
Option A:
Policy model + separate reference model
        ↓
Two models in memory
        ↓
Simple, but memory expensive
```

or, especially with LoRA:

```text
One base Qwen model
       +
LoRA adapter
       ↓
enabled → policy πθ
disabled → reference πref
```

This second strategy is very attractive for your T4 because you don't need to keep **two complete copies** of Qwen in GPU memory.

### So the whole sentence means

> **Load Qwen as the trainable policy, optionally make it memory-efficient with 4-bit + LoRA, and decide how we'll calculate the frozen reference model's log-probabilities for the DPO loss.**

That is exactly what your **M2.1** milestone is asking you to establish before moving to actual DPO training.

Yes — **mostly**. Those three settings are directly related to the QLoRA paper, and you should understand them there.

They mean:

```text
bnb_4bit_quant_type: "nf4"
        ↓
How the weights are represented in 4-bit

bnb_4bit_compute_dtype: bfloat16
        ↓
What precision is used for computation

bnb_4bit_use_double_quant: true
        ↓
Quantize the quantization constants too
```

### 1. `nf4`

**NF4 = NormalFloat 4-bit.**

This is one of the main contributions of QLoRA.

The paper explains why ordinary INT4 isn't ideal for neural-network weights and introduces NF4.

So when reading the paper, definitely understand:

[  
W_{\text{FP16}}  
\rightarrow  
W_{\text{NF4}}  
]

---

### 2. `compute_dtype=bfloat16`

This is slightly different.

It means:

> The **stored weights** are 4-bit, but computations use BF16.

So don't confuse:

```text
storage precision ≠ computation precision
```

Conceptually:

[  
W_{4bit}  
\xrightarrow{\text{dequantize}}  
W_{\text{BF16}}  
\xrightarrow{\text{matrix multiplication}}  
\text{output}  
]

The QLoRA paper discusses the computation/storage distinction, while the exact Hugging Face `BitsAndBytesConfig` option is an implementation detail.

---

### 3. `use_double_quant=True`

This is another QLoRA idea.

Normal quantization requires **quantization constants/scales**.

QLoRA says:

> We can quantize those constants too.

Hence:

[  
\boxed{\text{double quantization}}  
]

The paper reports that this saves additional memory with little performance impact.

---

### What I'd recommend for you

When reading the QLoRA paper, focus on these sections/concepts:

```text
1. 4-bit quantization
       ↓
2. NF4
       ↓
3. Double quantization
       ↓
4. LoRA
       ↓
5. QLoRA
```

You **don't need to memorize the implementation arguments** like:

```python
bnb_4bit_quant_type="nf4"
```

yet.

Understand the underlying concepts first. Then when you see the config:

```python
BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_compute_dtype=torch.bfloat16,
    bnb_4bit_use_double_quant=True,
)
```

you'll be able to translate it immediately into:

> **"Store the frozen base model using NF4 4-bit quantization, compute in BF16, and additionally quantize the quantization constants."**

Yes, you **can apply LoRA to the FFN**. It isn't forbidden. The choice of target modules is mainly a **trade-off between parameter count, memory, and adaptation capacity**.

For a transformer layer, you can roughly think of it as:

[  
x  
\rightarrow  
\underbrace{\text{Self-Attention}}_{\text{Q,K,V,O}}  
\rightarrow  
\underbrace{\text{FFN}}_{\text{up, gate, down}}  
]

Your configuration:

```python
target_modules=[
    "q_proj",
    "k_proj",
    "v_proj",
    "o_proj",
]
```

puts LoRA on the **attention projections**.

### What are these?

For input:

[  
X\in\mathbb{R}^{T\times d_{\text{model}}}  
]

attention creates:

[  
Q=XW_Q  
]

[  
K=XW_K  
]

[  
V=XW_V  
]

and after attention:

[  
O=\text{Attention}(Q,K,V)W_O  
]

So:

```text
q_proj → W_Q
k_proj → W_K
v_proj → W_V
o_proj → W_O
```

LoRA replaces each trainable update with something like:

[  
W_Q' = W_Q + \frac{\alpha}{r}B_QA_Q  
]

and similarly for (K,V,O).

---

## But what about the FFN?

The FFN is usually something like:

# [  
\operatorname{FFN}(x)

W_{\text{down}}  
\left(  
\sigma(W_{\text{up}}x)  
\right)  
]

or, for modern gated architectures such as Qwen:

# [  
\operatorname{FFN}(x)

W_{\text{down}}  
\left(  
\operatorname{SiLU}(W_{\text{gate}}x)  
\odot  
W_{\text{up}}x  
\right)  
]

So Qwen has modules roughly like:

```text
Attention:
    q_proj
    k_proj
    v_proj
    o_proj

FFN:
    gate_proj
    up_proj
    down_proj
```

You **can** specify:

```python
target_modules=[
    "q_proj",
    "k_proj",
    "v_proj",
    "o_proj",
    "gate_proj",
    "up_proj",
    "down_proj",
]
```

Then LoRA is applied to both attention **and** FFN.

---

## Why often start with attention?

Because attention controls **how tokens interact with each other**.

For example, changing (W_Q,W_K) changes:

[  
QK^\top  
]

which determines the attention scores:

[  
A = \operatorname{softmax}  
\left(  
\frac{QK^\top}{\sqrt{d_k}}  
\right)  
]

Changing (W_V) changes what information gets aggregated, while (W_O) changes how that aggregated information is projected back.

So attention LoRA gives the adapter a strong way to modify:

[  
\text{contextual interactions}  
]

while keeping the number of trainable parameters relatively small.

---

## But FFN LoRA can be useful

The FFN contains a large portion of the parameters in many transformers.

It is responsible for a lot of the model's **feature transformation / representation processing**.

So adding:

```python
"gate_proj",
"up_proj",
"down_proj",
```

gives LoRA more capacity.

The trade-off is:

```text
Attention only
    ↓
fewer trainable parameters
    ↓
less memory
    ↓
lower adaptation capacity

Attention + FFN
    ↓
more trainable parameters
    ↓
more memory
    ↓
greater adaptation capacity
```

### For your DPO project

I'd treat this as an **experimental choice**, not a fundamental rule.

Start with:

```python
target_modules=[
    "q_proj",
    "k_proj",
    "v_proj",
    "o_proj",
]
```

because it's a clean, relatively lightweight baseline.

Then, if you want to investigate whether the adapter needs more capacity, try:

```python
target_modules=[
    "q_proj",
    "k_proj",
    "v_proj",
    "o_proj",
    "gate_proj",
    "up_proj",
    "down_proj",
]
```

and compare validation/evaluation performance.

The important conceptual point is:

[  
\boxed{\text{LoRA can be applied to any suitable linear layer; target_modules specifies where.}}  
]

It's **not** that LoRA is an "attention technique." LoRA is a parameter-efficient way of learning low-rank updates, and you choose which weight matrices receive those updates.
