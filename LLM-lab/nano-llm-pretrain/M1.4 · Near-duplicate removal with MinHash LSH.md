
This is one of the most important milestones in your pipeline. Unlike the previous stage (quality filtering), this one introduces an algorithm (MinHash + LSH) that almost every modern LLM data pipeline uses (Dolma, RedPajama, RefinedWeb, etc.).

But **don't start coding yet.**

# What you need to understand first

Only four concepts.

---

## 1. Exact duplicates

Very easy.

```
Doc A:
I love machine learning.

Doc B:
I love machine learning.
```

Hash both.

```
hash(A)
hash(B)
```

If hashes are identical

```
duplicate
```

Easy.

Problem:

```
I love machine learning.

I love machine learning!
```

Different hash.

Not detected.

---

## 2. Near duplicates

Example

```
I love machine learning.
```

vs

```
I really love machine learning.
```

or

```
I love machine learning!
```

or

```
Machine learning is something I love.
```

These are basically the same information.

Exact hashing completely fails.

---

## 3. Shingles

Instead of comparing whole documents...

Split into overlapping pieces.

Example

```
I love machine learning very much
```

Words

```
I
love
machine
learning
very
much
```

3-word shingles

```
I love machine
love machine learning
machine learning very
learning very much
```

Represent document as

```
{
"I love machine",
"love machine learning",
"machine learning very",
"learning very much"
}
```

Another document

```
I really love machine learning very much
```

becomes

```
I really love
really love machine
love machine learning
machine learning very
learning very much
```

Notice they already share

```
love machine learning
machine learning very
learning very much
```

Very similar.

---

## 4. Jaccard similarity

Now compare two shingle sets.

```
A

{
A
B
C
D
}
```

```
B

{
B
C
D
E
}
```

Intersection

```
{
B
C
D
}
```

Size = 3

Union

```
{
A
B
C
D
E
}
```

Size = 5

Similarity

```
3 / 5 = 0.6
```

That's Jaccard similarity.

Perfect duplicates

```
1.0
```

Totally different

```
0
```

---

Problem.

Doing this for

10 million documents

means

```
10M² comparisons
```

Impossible.

---

# MinHash

Instead of storing

```
400 shingles
```

Store

```
128 integers
```

called a MinHash signature.

Amazing property:

Similarity of signatures

≈

Similarity of original shingle sets.

So

```
400 shingles

↓

128 numbers
```

Much smaller.

---

# LSH

Even MinHash isn't enough.

Comparing every signature

```
10M²
```

still impossible.

LSH solves this.

Idea

Only compare documents that look similar.

Imagine putting signatures into buckets.

```
Bucket 1

doc1
doc9
doc17
```

```
Bucket 2

doc5
doc11
```

Only compare

```
doc1
doc9
doc17
```

with each other.

Not against every document.

Huge speedup.

---

# Therefore the pipeline becomes

```
Raw docs

↓

Normalize

↓

Shingles

↓

MinHash

↓

LSH buckets

↓

Candidate pairs

↓

Jaccard similarity

↓

Remove duplicates
```

This is almost exactly what Dolma does.

---

# Your implementation

You do **not** need to implement MinHash yourself.

Use

```python
datasketch
```

Install

```bash
pip install datasketch
```

Then your job is only

```
Read filtered parquet

↓

Create MinHash

↓

Insert into LSH

↓

If similar document exists

    drop

Else

    keep

↓

Write filtered shard

↓

Save report
```

# What you should read before coding (about 45–60 minutes total)

1. **Dolma §4 (30 min)** — Understand _why_ deduplication is needed, how they report statistics, and why it happens before packing. Don't try to copy their production code.
    
2. **`datasketch` MinHash LSH examples (20–25 min)** — Learn the API:
    
    - `MinHash`
        
    - `MinHashLSH`
        
    - `update()`
        
    - `insert()`
        
    - `query()`
        

That's enough to implement a solid educational deduplication stage.

I would **skip Dolma's `deduper.py` initially**. It's production-oriented and will add complexity before you've built a working version. After your implementation works, you can skim it to compare designs.
